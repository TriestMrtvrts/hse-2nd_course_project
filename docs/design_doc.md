# Design Doc

## Проблема

Студенты и абитуриенты НИУ ВШЭ регулярно задают повторяющиеся вопросы по нормативным документам: аттестации, пересдачам, дисциплинарным мерам, порядку поведения в корпусах и организационным правилам. Ответы на такие вопросы должны быть:
- точными;
- опирающимися на официальный документ;
- понятными пользователю без юридического пересказа на несколько страниц.

## Целевая аудитория

- студенты бакалавриата и магистратуры;
- абитуриенты;
- сотрудники учебных офисов как внутренние пользователи инструмента;
- администраторы бота, которые загружают и обновляют документы.

## Бизнес-цели

- сократить время поиска ответа в длинных нормативных документах;
- снизить нагрузку на сотрудников, отвечающих на типовые вопросы;
- повысить прозрачность ответов за счет явной привязки к источникам;
- уменьшить число ситуаций, когда пользователь получает устный пересказ без ссылки на документ.

## Технические цели

- построить воспроизводимый RAG-конвейер для документов ВШЭ;
- обеспечить устойчивый retrieval на переформулированных и шумных запросах;
- поддержать обновление корпуса без полной ручной переразметки;
- разделить оценку retrieval и generation, чтобы видеть источник ошибок;
- подготовить инфраструктуру для сравнения embedders, чанкирования, sparse/dense поиска и reranking.

## Не-цели

- не заменять официальный юридический источник;
- не давать консультации вне корпуса загруженных документов;
- не автоматизировать принятие административных решений;
- не решать все диалоговые задачи университета одним ботом.

## Пользовательский сценарий

1. Пользователь задает вопрос естественным языком в Telegram.
2. Система извлекает релевантные фрагменты нормативных документов.
3. Бот либо показывает найденный контекст, либо формирует краткий grounded-ответ.
4. Пользователь при необходимости открывает документ-источник и перепроверяет правило.

## Критерии успеха

### Бизнесовые
- пользователь получает ответ быстрее, чем при ручном поиске по pdf/docx;
- ответ содержит понятную отсылку к документу;
- типовые вопросы по аттестации и внутреннему распорядку закрываются без вмешательства сотрудника.

### Технические
- doc-level retrieval устойчив на точных, перефразированных и шумных вопросах;
- разделимые эксперименты по preprocessing, chunking, embedders и retrievers воспроизводятся скриптом;
- generation оценивается отдельно, а не “по ощущениям”.

## Риски

- слишком маленький gold set приводит к нестабильным выводам;
- один только dense retrieval может проседать на аббревиатурах и редких формулировках;
- генерация без строгого grounding может вносить галлюцинации;
- плоское чанкирование может терять структуру документов и смешивать несвязанные нормы.

## Текущее решение

- конвертация документов в markdown;
- предобработка и чанкирование;
- dense retrieval по эмбеддингам;
- Telegram-интерфейс;
- отдельный экспериментальный контур для retrieval и generation оценки.

## Следующие шаги

- расширять корпус документов;
- усиливать retrieval за счет sparse/ensemble/rerank;
- проверять AgenticRAG-подходы на пограничных вопросах;
- наращивать gold set и generation eval set вместе с реальными пользовательскими логами.
